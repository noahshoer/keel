# Keel

A standalone, local-first, Todoist-style task app with streaks, written in Rust: **Tauri v2** shell + **Dioxus 0.6** UI compiled to wasm. It's not a Todoist client and has no Todoist dependency; Todoist's UI was the starting reference, and Keel now has its own look (green `#268366` accent, a pine-reflection logo).

Owner: Noah (GitHub `noahshoer`, **public** repo `noahshoer/keel`; anything committed is visible to everyone, so never commit secrets, and keep Todoist reverse-engineering material out of the repo, as history was rewritten on 2026-10-20 to remove it). v1 targets **iOS**, minimum **iOS 26** (`bundle.iOS.minimumSystemVersion`). Windows desktop is the development target, and everything except the iOS build has been built and tested there.

A completed task once still notified because a failed cancel forgot its id. Upstream issue draft (not yet filed): `docs/notes/upstream-notification-ios-issue.md`.

- Tapping a notification from an earlier run crashed the app (plugin force-unwrap). Fixed with a vendored, patched `tauri-plugin-notification` in `crates/vendor/` (`[patch.crates-io]`). Not yet confirmed on the phone; see [docs/notes/ios-notification-tap-crash.md](docs/notes/ios-notification-tap-crash.md) if it recurs.

After iOS: **sync** (dormant by design). Every change already goes through an idempotent command log, so the plan is to swap rusqlite for libSQL and add Turso, plus some device-link model. Then integrations (Apple Reminders, MS To Do, Google Calendar, Outlook, Notion). Spec non-goals for v1: comments, attachments, location reminders, collaboration, templates, activity log, backups.

v1 features done: projects, sections, sub-tasks, labels, filters (query language), priorities, due dates and times, deadlines, recurrence (incl. intervals, yearly, last day/workday, nth weekday), streaks, natural-language quick add with live highlighting, search, completed-task view, local notifications (global rule + per-task reminders + daily summary), dark mode, responsive layout, and Todoist CSV import (Settings → Import; `core::import::{csv, todoist}`, `AppService::import_todoist_csv`).

Task view (2026-10-23, spec `docs/superpowers/specs/2026-10-23-task-view-design.md`): tapping a task opens its view, a sheet on the phone (swipe down on the header or tap the scrim to close) and a 360px right panel on desktop windows at least 900px wide (`ui::task_view::{nav, view, fields}`). It has the title and description edited in place, field rows plus dotted "+ Field" pills for what's missing (each opens the native picker on iPhone and saves at once), a ••• menu (Streak on repeating tasks, Delete), and a sub-task card ("x of y · Show completed", "+ Add sub-task"). Opening a sub-task pushes its view; Back pops it. On the phone, a swipe in from the left edge inside a sub-task is an interactive Back (`gestures`: `edge_back_action`, `edge_back_commits`; scenario `scripts/sim-checks/edge-back.js`). Lists are cards (`core::views::cards`, `ui::cards`): sub-tasks are hidden under their parent's "x/y" count, and dated views group matching sub-tasks under their top-level parent's header. Completing a parent completes its sub-tasks; completing a repeating parent moves its date and unchecks its sub-tasks (part of `TaskComplete`, no new `Action`); deleting a task deletes its sub-tree.

## Layout

| Crate | Package | What |
|---|---|---|
| `crates/core` | `keel-core` | Pure domain: `model`, `commands` (Action enum + `apply_at`), `recurrence`, `streak`, `filter` (query language), `quickadd` (NL parser + spans), `reminders` (notification planner), `search`, `calendar`, `views`. Host-tested, no I/O. |
| `crates/storage` | `keel-storage` | `SqliteRepo` (rusqlite, bundled) implementing `Repository`. Schema in `migrations.rs`; `local_setting` table holds device-local prefs (never synced). |
| `crates/service` | `keel-service` | `AppService`: views, dispatch, search, reminder settings and plan. |
| `crates/src-tauri` | `keel` (lib `keel_lib`) | Tauri IPC wrappers + `notifications.rs` (iOS: schedule with the OS; desktop: 20s ticker thread). App id `com.nshoe.keel`, store `keel.db`. |
| `crates/plugin-ios` | `tauri-plugin-keel-ios` | What Keel needs from Swift on iOS, nothing else: the diag log (`Diag.swift`), keyboard pace (`Keyboard.swift`, `window.keelKeyboard`), the sim-check script runner (`Script.swift`, `KEEL_SCRIPT`). Always loaded. |
| `crates/plugin-glass` | `tauri-plugin-glass` | **Parked** Liquid Glass controls (card, buttons, menus). Optional dep behind the `keel` crate's `glass` feature; only `tauri.conf.json` (the Dioxus build) turns it on, so the React build never loads it. Logs through `GlassLog` (a `keel.diag.line` notification that `Diag` writes). |
| `crates/core-wasm` | `keel-core-wasm` | wasm-bindgen exports of `keel-core` for the web UI (typed bindings; built by `web/scripts/build-wasm.ts`). |
| `web/` | (pnpm) | React + TypeScript frontend, in progress; see below. |
| `crates/ui` | `keel-ui` | Dioxus web/wasm UI. **Excluded from the workspace**, so build it with `dx`. Talks to Rust via `window.__TAURI__.core.invoke` (`api.rs`). |

Design spec: `docs/superpowers/specs/2026-10-19-todoist-tauri-port-design.md`. Each phase has a plan in `docs/superpowers/plans/` with its decisions and notes.

## Build, test, run

CI (`.github/workflows/ci.yml`, runs on every push): **Windows** runs the tests, the UI tests and wasm check, the web UI build, and `cargo tauri build --no-bundle`. **iOS** (`macos-26`) runs `cargo tauri ios build --target aarch64 --debug --no-sign --ci` (iPhone target; the simulator target fails on the runner's Xcode) plus a simulator Rust build. An Ubuntu **`web`** job runs `pnpm check`, the web build, `scripts/check-bindings.sh`, `pnpm audit` and an OSV scan; the weekly `web-supply-chain.yml` repeats the audit on `main`. The web UI is built first in both jobs (the Tauri crate won't compile without `crates/ui/dist`). Verification only: nothing is signed or deployed. Keep `DX_VERSION` / `TAURI_CLI_VERSION` in the workflow in step with the local tools.

```bash
cargo test                                   # core + storage + service (UI excluded)
cd crates/ui && cargo check --target wasm32-unknown-unknown   # UI type-check (0 warnings expected)
cd crates/ui && dx build --platform web && cp -r target/dx/keel-ui/debug/web/public/* dist/
cd crates/src-tauri && cargo tauri dev       # desktop app (serves crates/ui/dist)
```
- Tauri's `frontendDist` is `crates/ui/dist` (git-ignored). **Rebuild and copy after every UI change**, then restart or reload the app.
- `dx` 0.7.x prints "dx and dioxus versions are incompatible" against Dioxus 0.6.3. It's harmless; the build completes. Because of that mismatch, Dioxus' `asset!` doesn't bundle files, so the Inter font is embedded as base64 data URLs in `style.rs`.
- App icons come from `crates/src-tauri/icons/keel.svg`: `cd crates/src-tauri && cargo tauri icon icons/keel.svg`. The sidebar logo is `icons::logo()` in `crates/ui/src/icons.rs`; keep the two in sync.
- Stop a running `cargo tauri dev` before big builds. Its watcher rebuilds on file changes and fights over `target/debug/keel.exe`.

## React frontend (in progress)

`web/` is the React + TypeScript app that will replace `crates/ui` (strict TS, Vite, Vitest, Biome, pnpm; Node 24). It has every list screen (Plan 2, `docs/superpowers/plans/2026-10-30-react-lists-and-rows.md`): all views, sections, completing and reopening, streaks, the sidebar's add / rename / delete forms, filters with live checks, search with `/` and Cmd+K, the theme, the drawer and long-press row actions. It also has the editor (Plan 3, `docs/superpowers/plans/2026-10-30-react-editor-and-quick-add.md`): "+ Add task" rows in every list open `web/src/editor/TaskEditor.tsx` with quick-add highlighting, preview chips, Todoist's backspace, and the date (calendar, month / year wheels, time), deadline, reminder, priority, repeat, project and label pickers; its edit mode and `saveEdit` wait for the task view. The editor's data rules are `keel_core::editor` (shared with the Dioxus editor): `editorView` gives everything the editor draws from one parse, and `addPlan` / `editPlan` give what saving sends. Not yet: the task view and gestures (Plan 5, next: write its task-by-task plan from roadmap item 5, in the style of the Plan 2 and 3 files), Settings (Plan 6). Plan 4 (glass) is deferred. The Dioxus UI keeps shipping until the cutover: `tauri.conf.json` still points at `crates/ui/dist`, and the React app runs through the overlay config `crates/src-tauri/tauri.react.conf.json` (`devUrl` `http://localhost:5173`, `beforeDevCommand` `pnpm dev` and `beforeBuildCommand` `pnpm build`, both with cwd `web/`, `frontendDist` `web/dist`).

Fresh machine: Node 24 (Homebrew `node@24`, on PATH via `~/.zshrc`), `corepack enable` once, `cd web && pnpm install`, and the project-local wasm-bindgen from the repo root: `cargo install wasm-bindgen-cli --version 0.2.129 --locked --root .tools` (`.tools/` is git-ignored).

```bash
cd web && pnpm check                     # wasm build, tsc, Biome, Vitest, dependency vetting
cd web && pnpm dev                       # browser at http://localhost:5173 with the mock backend
cd crates/src-tauri && cargo tauri dev --config tauri.react.conf.json       # desktop, HMR
cd crates/src-tauri && cargo tauri ios dev --config tauri.react.conf.json   # phone over Wi-Fi, HMR
cd crates/src-tauri && cargo tauri build --no-bundle --debug --config tauri.react.conf.json
```
- `pnpm dev` builds keel-core's wasm (`scripts/build-wasm.ts`), then `scripts/dev.ts` runs Vite and `scripts/watch-wasm.ts`. The watcher rebuilds the wasm when `crates/core/src` or `crates/core-wasm/src` changes and logs one line per rebuild (`watch-wasm: rebuilt in 1.5s (…)`). A failed build prints cargo's error and it keeps watching. Vite reloads the page when the new `src/core/pkg` lands. The watcher stops when the dev server does. Edits to `web/src` hot-reload without restarting Rust.
- With `cargo tauri ios dev`, Tauri swaps the `localhost` in `devUrl` for the Mac's address and sets `TAURI_DEV_HOST`, and `vite.config.ts` binds to it, with HMR on port 1421.
- Styles are `web/src/styles/app.css`, moved verbatim from `crates/ui/src/style.rs` (Biome skips that file). Until the cutover, a CSS change goes in both. Inter loads as files from `web/src/assets/fonts`.
- Diagnostics: `web/src/diag.ts` ports `crates/ui/src/diag.rs` exactly (the same `diag_log` sources and hooks, installed only while logging is on). The React app has no Settings screen yet, so turn logging on from the Dioxus build's Settings (the setting is device-local in `keel.db` and stays on), or use `KEEL_DIAG=1` on the desktop.
- **Liquid Glass is parked** (Noah, 2026-10-30). The React app never calls `plugin:glass|*` and always takes the Dioxus no-glass paths (header menu button, inline forms, hover or long-press row actions). Its build doesn't load the glass plugin at all (`glass` feature off in `tauri.react.conf.json`), so no overlay is attached. The glass code stays for later. Parity on iPhone means parity with the Dioxus app's no-glass behavior.
- Data rules come from `keel-core` through `web/src/core` (`dateGroups`, `upcomingTasks`, `dueBucket`, `deadlineUrgent`, `reminderLabel`, `allDone`, `cards`, …); TypeScript never compares a task's date to today. Command return types are generated (`web/src/bindings/Commands.ts`, from `crates/src-tauri/tests/commands_list.rs`).
- Forms opened by a tap focus their field inside the tap (`web/src/shell/focus.ts`), so iOS raises the keyboard.
- The screens reuse the Dioxus markup and class names, so `app.css` applies unchanged and `Demo.swift` and `scripts/sim-checks/*.js` find what they query (`.sidebar`, `.brand .theme-toggle`, `.task-row`, `.task-body`, `.task-content`, `.task-badges`, `.task-count`, `.task-project`).

## Conventions

- Workflow per phase: write a short plan in `docs/superpowers/plans/` → feature branch → **TDD** (failing test first) → commit per task → merge `--no-ff` to `main` → push. Noah prefers you build without asking for routine decisions; ask about genuinely personal choices (names, visual direction), ideally with visual options.
- **Where logic lives.** The test is whether it's about the data or about the screen, not which platform uses it.
  - Data rules go in `keel-core`, with Rust tests: what's true about tasks, dates, recurrence, quick-add parsing, filters, views and grouping, streaks, what an edit changes. The frontend calls them through IPC or the wasm build (`crates/core-wasm`) and never re-implements them in TypeScript, not even a small copy.
  - Screen rules stay in the frontend, typed and tested with Vitest: components (shared by the desktop and phone layouts or not), layout, gestures and sheet detents, keyboard timing, navigation, focus. Interaction logic lives in plain `.ts` modules with tests, and components connect it through hooks.
  - If a frontend function starts deciding something about a task (its next date, whether it's overdue, how it groups), move it to `keel-core`.
- Tauri commands use `#[tauri::command(rename_all = "snake_case")]`. Each takes one `…Args` struct from `crates/src-tauri/src/args.rs` (`NoArgs` when there are no parameters; the parameter is named `_args`, which Tauri still binds as `args`), and callers send `{ args: {...} }` with snake_case fields. Adding a command means: the fn in `lib.rs`/`diag.rs`, its Args struct, an entry in `command_args!` in `crates/src-tauri/tests/commands_list.rs`, an entry in `web/src/ipc/commands.ts` (plus a mock handler), and regenerating bindings with `scripts/check-bindings.sh`. Return types in `commands.ts` are hand-written for now.
- A command that calls into a mobile plugin (anything touching `app.notification()`, including `notifications::resync`) **must be `async`**. A sync command runs on the main thread and blocks it waiting for Swift, which deadlocks against any other plugin call that needs the main thread. That froze the app when Settings opened next to a glass-plugin call.
- Commands are idempotent (uuid) with temp-id → id mapping. Add new `Action` variants (never change existing serialized shapes); new fields are `#[serde(default)]`. Adding a field to `TaskAdd`/`TaskUpdate` means updating struct literals in tests too.
- `Recurrence` variants are append-only (stored as JSON in `Due`). Consumers only use `contains` / `next_after` / `prev_before`.
- Quick add: an unrecognized `every …` phrase stays text as a whole (no silent misreads). A phrase on its own still highlights and applies (Todoist-style), but the editors won't save until there's a name besides it (`editor::has_name`, `CardState.can_submit`).
- UI: one popover open per editor (`OpenPop`), fixed-positioned on mount by `pickers::place_popover`. Task reminders are shared through Dioxus context (`Signal<Vec<Reminder>>`). A global capture-phase `submit` listener in `App` prevents native form submits, because Dioxus' `prevent_default()` isn't honored on submit and the page would reload.
- On Windows the working tree is CRLF (`core.autocrlf=true`). Use exact-string edits; shell regex edits across lines are fragile.

## Verifying UI changes

- **Browser preview with a mock backend:** serve a copy of `dist/` whose `index.html` defines a fake `window.__TAURI__.core.invoke` returning sample data (one handler per IPC command; it receives `{ args }`). `web/`'s `pnpm dev` already has a built-in mock backend. Good for layout, dark mode and 375px checks.
- **The real app over the WebView debug port (Windows):** run `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223 cargo tauri dev`, then drive the page with CDP `Runtime.evaluate` from a small Node script (`fetch('http://127.0.0.1:9223/json')`, then a WebSocket to the page). This is how deadlines, reminders and notifications were verified end to end. Desktop reminders log `reminders: showed …` to the dev console.
- Don't screen-capture the desktop or steal window focus to check the app.

**Diagnostics log (permanent, off by default):** Settings → Diagnostics logging (device-local `diag_enabled` setting) or `KEEL_DIAG=1` (simulator: `SIMCTL_CHILD_KEEL_DIAG=1 xcrun simctl launch …`) turns it on; while off nothing is written and no JS hooks are installed. One log collects Swift (keyboard, scroll view, overlay frames, card show/hide), Rust and the page: `diag::log("source", "msg")` in `src-tauri` (`crates/src-tauri/src/diag.rs`), `diag::log("msg")` in the UI (`crates/ui/src/diag.rs`, which also captures JS errors, unhandled rejections, `console.error` and wasm panics), `Diag.log("msg")` in Swift; Rust panics are captured too. iOS writes `Library/Caches/diag.log` (Swift, `Diag.swift`); desktop writes `diag.log` in the app data dir. Both roll over at ~2 MB to `diag.1.log`. Pull it with `scripts/diag.sh` (phone; or `scripts/diag.sh <simulator-udid>`), saved timestamped under git-ignored `diag-logs/`; `scripts/diag.sh --fresh <udid>` clears a simulator's log first; on the phone, switching the setting on starts a fresh log (the last one becomes `diag.1.log`). Logging only ever touches `diag.log` / `diag.1.log`, never `keel.db`. **Never** write into the phone's app container with `devicectl device copy to --remove-existing-content`: it empties the whole container, `keel.db` included (it wiped Noah's tasks on 2026-10-28). Add temporary hooks for a specific bug through these calls rather than a throwaway commit.
